## Before the Team

### Consumer Products at Scale

I contributed product design to consumer applications used by millions of people. The work covered onboarding, core task flows, settings, notifications, and the unglamorous surfaces where most of the experience actually lives.

What I learned: at scale, the default is the product. Almost nobody changes the settings, so the default has to be right for the person who is distracted, impatient, and on a bad connection.

### A Design System and Its Foundations

Tokens, component contracts, patterns, and documentation for a multi-surface product. The work included the type scale, the spacing rhythm, the color roles, the empty and error state conventions, and the review standards that kept new work inside the system.

What I learned: a design system is decisions, not components. The components without the reasons become a museum within a year.

### Copy as an Interface Layer

A full pass over product language: error messages, empty states, onboarding, button labels, confirmation dialogs, and the tone rules that connected them.

What I learned: copy is the cheapest high-leverage design material. A better sentence can fix in minutes what a layout change cannot fix in a week.

### Editorial and Marketing Surfaces

Art direction and page design for product storytelling: pricing comparisons, feature narratives, launch pages, and long-form editorial layouts.

What I learned: a marketing page is a product surface. The same rules apply: one job per section, hierarchy that reads at a squint, honest numbers, and copy that says what happens rather than what to feel.

## Current Work

### Product Design Ownership

- Page and flow specifications with acceptance criteria written as observable outcomes
- Component and state coverage across empty, loading, error, disabled, and overflow conditions
- Information architecture built around user mental models rather than organizational boundaries
- Copy for every surface, including the failure paths

What I learned: a specification is finished when an engineer can build from it without asking a question, and not before.

### Design System Stewardship

- Four-level architecture: foundations, components, patterns, surfaces
- Token-driven typography, spacing, color, and motion
- Component contracts that make the right usage easy and the wrong usage visible
- Documentation written for the person who arrives without context

What I learned: the system has to teach itself. If using it requires asking me, it is not finished.

### Frontend Verification

- A repeatable protocol for checking work in the live surface at real widths
- State, responsive, keyboard, contrast, and theme checks
- Last-mile fixes for spacing, copy, and transitions rather than a list of complaints
- A review loop that keeps code review and design verification as separate checks

What I learned: an approval is a claim. The evidence has to exist before the claim does.

### Interface Design for an Agent Product

- A design language for a terminal and chat surface: message structure, state language, tool activity, and calm progress feedback
- A design system for system-level foundations rather than isolated screens
- Information architecture for agent activity that stays legible as it grows
- Copy that makes a technical surface feel like a companion rather than a console

What I learned: internal orchestration data is not user-facing content. The right abstraction is a one-line summary, not a raw payload.

### Brand and Visual Craft

- Hand-built product visuals rather than stock assemblies
- Type and palette systems that hold across light and dark surfaces
- Art direction that treats a marketing page as a designed object, with a reason for every element

What I learned: CSS cannot fake ink. If a mark needs to feel drawn, it has to be drawn, and the details that make it feel authored are the ones nobody lists.
